# 后台系统规划

记录日期：2026-09-14。前端适配更新：2026-09-15。

本文记录后续开发要求、已完成的前端适配与建议的数据设计。目录读取层已优化，但后台、数据库、登录、图片上传或实时更新尚未实现。内部讨论链接不写入仓库。

## 已确认的目标

爸爸以后通过电脑、平板或手机浏览器打开后台，就能管理网站内容。后台也是网页版。

内容层级为：

```text
机构
└── 一级分类
    └── 二级分类
        └── 商品 / 配套
```

机构、一级分类、二级分类及商品都需要支持后台维护，包括新增、编辑、排序、发布和隐藏。富贵山庄与云南善堂的数据按机构区分。公共网站保留现有五个主导航；产品分类展示在对应机构页面内部。

例如，在富贵山庄新增与「福地」同级的「福星地」，再新增「单人」「双人」「家庭」二级分类。发布后，用户端自动显示新入口与相应产品，无须修改 React 页面或重新部署。这个例子仅说明未来功能，不代表现在新增实际产品。

## 排序与推荐

| 对象     | 排序范围             | 规则           |
| -------- | -------------------- | -------------- |
| 机构     | 全部机构             | 后台可调整     |
| 一级分类 | 同一机构下的一级分类 | 独立排序       |
| 二级分类 | 同一父分类下的子分类 | 独立排序       |
| 商品     | 同一个所属分类内     | 独立排序       |
| 首页推荐 | 首页推荐列表         | 与目录顺序分开 |

新增内容默认排在所属列表最后。后台支持拖拽调整，也提供向上、向下移动按钮，以便手机和键盘操作。点击「保存排序」后才保存；失败时保留原有公开顺序，并允许重试。

目录使用 `sort_order`；首页推荐使用 `is_featured` 与 `featured_order`。将新项目插入第二位时，原有第二位及后续项目顺延。保存整组顺序应作为一次原子操作，避免只保存部分条目。

## 建议的数据模型

以下是后续数据库设计依据，不是本轮新增的运行接口。数据库字段与前端 TypeScript 字段通过数据读取层转换。

| 数据对象             | 主要字段 / 职责                                                                                                       |
| -------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `providers`          | `id`、`slug`、名称、简介、封面、`sort_order`、`status`                                                                |
| `categories`         | `id`、`provider_id`、`parent_id`、`slug`、名称、简介、封面、`sort_order`、`status`、`show_in_catalog`、`display_mode` |
| `products`           | `id`、`provider_id`、`slug`、名称、说明、价格、分期、区域、规格、服务阶段、`status`、`is_featured`、`featured_order`  |
| `product_categories` | 商品与分类的对应关系，以及该分类中的商品 `sort_order`                                                                 |
| `product_images`     | 图片存储路径、替代文字、封面标记、`sort_order`                                                                        |
| `advisor_profile`    | 顾问资料、联系方式、个人照片、服务经历                                                                                |
| `site_content`       | 首页文案、服务理念、园区资讯与其他展示内容                                                                            |

分类以稳定的 `id` 建立关联，以 `slug` 构成网址。`parent_id = null` 表示一级分类；子分类使用父分类的 ID。首先落实当前所需的两级分类，后续可以沿用父子关系扩展层级。

`show_in_catalog` 控制入口是否在目录展示；它不等于发布权限。未发布内容不能通过直接输入网址或公开数据接口读取。隐藏父分类时，其子分类和产品也不能从该路径公开访问。删除存在子分类或商品关联的分类时，应要求先迁移关联内容，避免误删整组资料。

分类树需要防止循环引用、跨机构父子关系，以及无效分类关联。分类网址在同一机构内唯一；已发布网址变更时需要处理旧地址。

现有福地产品可同时属于「双人」和「火化土葬」，所以不能机械地将 `tags` 改成单一二级分类字段。使用商品与分类的关联表保留这种多分类筛选能力。一级分类的「全部」统计应对商品去重。

## 已完成的用户端适配（2026-09-15）

| 位置                                                   | 现在的实现                                                                        | 下一阶段                               |
| ------------------------------------------------------ | --------------------------------------------------------------------------------- | -------------------------------------- |
| `src/types/index.ts`                                   | 通用机构、分类、产品、关联记录与目录快照；稳定 ID 和 slug 分开                    | 对齐数据库字段、接口验证与迁移         |
| `src/data/catalog.ts`                                  | 两个机构、六个一级分类、十三个二级分类、29 个产品及 58 条分类关联；显式状态与排序 | 将公开种子资料迁入数据库               |
| `src/catalog/repository.ts`                            | 统一处理公开展示、祖先状态、机构隔离、去重、搜索、目录排序、推荐排序及旧筛选值    | 接入经过权限过滤与验证的远程数据       |
| `src/catalog/context.tsx`                              | 接收 `CatalogSnapshot`，向全部目录页面提供一致的读取入口                          | 远程加载、错误与空数据处理、刷新或订阅 |
| `src/pages/Nirvana.tsx`、`CatalogueSection.tsx`        | 通用机构目录，由资料生成分类入口、数量和介绍，不再固定写六类                      | 后台配置机构与目录资料                 |
| `src/pages/Category.tsx`                               | 通用父子分类页，以 ID 筛选；比较表和咨询入口由配置控制                            | 后台编辑分类展示设置                   |
| `src/pages/PackageDetail.tsx`、`src/components/ui.tsx` | 通过读取层获取产品；处理无效关联、缺失价格和部分分期字段                          | 后台录入产品、图片及详细内容           |
| 首页                                                   | 按 `isFeatured` / `featuredOrder` 读取独立推荐列表                                | 后台选择与排序                         |
| 云南善堂                                               | 保留现有服务页面，配置产品分类后自动增加目录区域                                  | 录入确认后的机构与产品内容             |

公开路由使用 `/:providerSlug/:categorySlug` 与 `/:providerSlug/packages/:slug`，原有网址保持兼容。新增分类不再需要新建页面组件。内部关联使用稳定 ID；后台改名时应保留 `legacyFilterValues`，继续兼容过去以中文标签构成的筛选网址。

商品的 `categoryId` 是主分类；`productCategories` 记录其在主分类和其他子分类中的展示位置及排序。隐藏主分类会隐藏对应商品；隐藏某个次要子分类仅移除该路径中的展示，不影响其他已发布分类的关联。一级分类聚合后按商品 ID 去重，若同时存在直接关联与子分类关联，优先使用该一级分类中的显式排序。

`nextSortOrder` 为指定同级列表提供新增末位序号；`reorderRecords` 生成完整、无重复的排序草稿。它们目前是可测试的纯函数，没有保存接口或后台拖拽界面。后台实施时仍需校验操作范围，并将排序原子保存。

「全部」是前端操作，不是数据库分类。「其他 / 咨询」是 `inquiryOption` 配置。比较表通过 `displayMode` 控制；仪式说明来自产品的 `ritualNote`，不再从名称或网址猜测。

当前仍使用本地资料，修改它们仍要部署才能让线上页面更新。读取层已能接收新快照，但并未连接远程数据库或提供后台保存功能。顾问资料和非目录页面文案仍保存在 `src/data/site.ts` 等现有文件中，后续接入后台。

客户端状态过滤只是展示规则，不能代替数据库权限；当前种子文件只应保存允许公开的资料。未来的数据服务必须在服务器或数据库侧阻止未发布内容和管理信息被公开下载。

## 后台页面范围

- 管理员登录与退出。
- 机构管理。
- 一级 / 二级分类管理，包含发布状态、目录展示与排序。
- 商品列表与编辑，包括分类选择、服务内容、规格、价格及图片。
- 首页推荐选择与独立排序。
- 个人资料、联系方式与网站文案管理。

价格统一使用「生前规划价（Pre-Need）」和「即时需求价（As-Need）」。需要区分配套类型时，使用「生前规划配套（Pre-Need）」和「即时需求配套（As-Need）」。

当前咨询表单只预览文字。将来如果需要真正接收和管理客户留言，应另行实现提交、隐私说明与后台访问权限，不能把现在的预览当成已发送。

## 数据服务与更新边界

后续可按原规划使用 Supabase 管理数据、管理员身份与图片。正式接入前另行完成数据库迁移、访问规则与账号配置。部署平台选择单独处理，本轮不迁移现有网站托管。

「不需要重新部署」适用于新增、编辑、排序、上下架等内容变更。新增业务功能或全新页面模板仍可能需要开发与部署。

保存成功后，后续页面请求应读取新数据。已经打开的页面如要同步变化，需要显式设计数据失效刷新或变更订阅，并处理断网恢复；不能只接数据库就宣称实现实时更新。

公开端只读取允许公开的资料；写操作必须验证管理员权限，不能仅依靠前端隐藏按钮。数据库管理密钥不得进入网页构建文件。正式实现时还需覆盖图片上传限制与后台操作校验。

## 实施顺序

1. 用户端布局与字段确定后，将现有类别、筛选及商品梳理为可迁移数据。
2. 分离稳定 ID 与 slug，增加机构、父子关系、状态、目录排序及推荐排序；建立统一读取层。
3. 建立数据库结构、数据迁移与访问规则，再接入用户端读取。
4. 实现后台登录、内容编辑、图片上传与排序保存。
5. 接入公开页面的数据刷新机制，进行完整权限及流程验证。

## 完成标准

- 后台新增并发布「福星地」后，用户端无需部署即可出现新目录入口。
- 新建「单人」「双人」「家庭」子分类及产品后，筛选结果、详情、数量和咨询主题均正确。
- 新增默认排最后；拖至第二位保存后，相应同级列表顺序正确，其他机构或父分类不受影响。
- 首页推荐可以独立调整，不改变商品目录顺序。
- 更改分类名称不破坏商品关联；隐藏内容在列表、直接网址及公开接口中均不可读取。
- 原有七款骨灰殿产品、聚雅阁 / 腾黄阁独立筛选和产品网址继续可用。
- 同时属于多个子分类的商品不会在一级分类中重复出现。
- 保存失败不会显示发布成功；访客不能写入或读取未发布资料。
- 电脑、平板和手机都能管理内容，不依赖仅桌面可用的拖拽操作。
