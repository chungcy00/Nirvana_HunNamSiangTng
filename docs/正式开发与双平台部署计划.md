## 3. 已有接口与需要补齐的能力

当前 `api` 恰有七个 RPC：

| 已有 RPC | 正式开发中的用途 |
| --- | --- |
| `current_catalog_member()` | 每次会话验证有效后台成员及数据库角色 |
| `admin_product(p_id)` | 授权后台读取整件产品与关联资料 |
| `save_product(p_id, p_expected_updated_at, p_product, p_changes)` | 新建／修改、草稿保存、发布与隐藏；多表一次提交，保留数据库校验 |
| `delete_draft(p_id, p_expected_updated_at)` | 仅删除从未发布的草稿 |
| `catalog_product_list(...)` | 网站公开列表与筛选结果 |
| `catalog_product_detail(p_slug)` | 网站公开详情 |
| `catalog_product_prices(p_id)` | 网站公开价格 |

以下是现有需求尚缺的服务入口，拟通过增量 RPC／服务端编排实现，**不增加业务表或字段**。函数名为计划名称，实施时核对实际签名：

| 缺口 | 拟补齐方式与边界 |
| --- | --- |
| 后台列表、搜索、分页、系列及状态筛选 | 新增授权 `admin_product_list`；不使用只能读已发布资料的公开列表冒充后台列表 |
| 园区／系列、宗教字典、通用备注读取与维护 | 有限字段、固定对象的读取及保存 RPC；管理员写，编辑员按需读。沿用现有表及外键、停用规则 |
| 七大类别独立排序与新增排末尾 | 原子 `reorder_category_products`，提交类别全量 ID 及每条原 updated_at，校验集合完整、无重复、不跨类、版本未变化；新增／重分类在锁内计算该类末位序号 |
| 正式产品复制 | 服务端先复制所有图片至新私有路径，专用 RPC 在一个事务内重建产品及子表关系；失败清理新文件，不建立半成品产品 |
| 操作记录查看 | 管理员专用、限制字段和分页的读取入口；不向网页角色授予 audit_logs 原表权限 |
| 图片补偿清理 | 受信任服务端检查引用后清理无引用新文件，失败可重试；不新增清理业务表，不清理仍被引用的对象 |

这些属于第一阶段正式能力开发，不是重新建设数据库。新增入口仍固定 search_path、验证 auth.uid() 及有效成员，撤销默认 PUBLIC 执行权限；网页身份不得直接读取 private 表。字典写权限只授予受限执行角色并配套管理员 RLS，不把权限扩大给 authenticated。

当前 religion ID 为 smallint、系列及产品为 UUID，必须由数据库约束下生成／分配；不沿用 HTML 的 `uid()` 或角色文字作为正式身份。

### 必须单独解决的字段差异

HTML 与现有前台已使用安放环境，工作区存在待审 `20261021171754_niche_placement_type.sql`；但云端 `niche_details` 实际只有 `product_id`、`theme_name`、`niche_style`、`niche_notes`，没有 `placement_type`。四份主文档 1.3 也没有这个字段。

本计划不执行该待审脚本，不把室内／室外塞入主题、备注或产品名称冒充结构化字段，也不从系列名称自动推断。进入安放环境持久化验收前，需单独明确这个既有待审增量是否获准。其他第一阶段工作可独立推进；若仍维持“零字段增量”，该项必须明确列为尚未满足，不能宣称完整还原 HTML 或切换全部前台筛选。既有待审脚本还需按当前八份迁移基线重新审查，不能直接执行旧版本。

## 5. 第一阶段：后台正式开发

### 工作内容

1. 提取 HTML 的黑白侧栏、顶栏、列表、分区编辑器、弹窗、预览、移动导航和离页提示，改成 React 组件与类型明确的状态，不重设计既有 UI/UX。
2. 产品编辑按七类显示字段；保留人数合法值、四类宗教要求、共通与宗教专属项目、单价／多方案、骨灰位最低价及殡仪双价。默认方案与价格模式由数据库维护。
3. 接入现有保存／读取 RPC；补齐第三节列出的正式业务入口。所有变更保留原 updated_at；HTTP 409 保留未提交表单并引导核对，不自动覆盖他人内容。
4. 关联系列快速新增后选中；宗教快速新增后仅加入可选字典，不自动关联或公开。重复名称、停用系列、已引用字典等规则在服务端检查。
5. 图片先创建真实草稿取得产品 ID，再上传 UUID 新路径；不覆写旧文件。图片引用跟随整件产品提交，提交失败的无引用文件走补偿清理。
6. 复制先读取源版本，重建所有 ID 与 offer 映射，清空内部代码、备注及来源，公开开关全部关闭。复制前源产品与关联需保持版本一致，整个数据库复制只提交一次。
7. 复制文件存在先后依赖：现有 Storage 策略要求目标产品存在，而需求不允许留下半成品产品。因此先由受控服务端准备新私有文件，再由专用复制 RPC 原子创建目标；不能由浏览器临时放宽 Storage 权限解决。
8. 删除演示角色下拉、模拟故障开关、浏览器产品数据库、恢复演示数据与假保存成功。Auth SDK 的正常会话持久化、筛选偏好可保留；它们不决定角色，也不保存正式业务数据。
9. 管理员设置页显示真实身份和权限维护说明，账户增删／提权仍经受控维护流程；不照抄 HTML 的自由角色切换。
10. 云南善堂保留占位页。公开前台云南善堂内容不因后台占位而删除。

## 6. 第二阶段：登录及权限

实现真实密码登录、退出、会话恢复、过期处理及必要的密码恢复回调。每次进入后台验证 current_catalog_member；被停用账户即使仍有 JWT，也不能读取后台资料或受限图片。普通登录用户不因 authenticated 身份取得后台权限。编辑员只改从未发布的草稿，管理员负责正式修改、发布、隐藏、字典及排序。

分别验证匿名、无成员身份、编辑员、管理员、停用成员；覆盖直接 RPC、原表访问、Storage、后台预览、复制、价格事务和审计。检查打包产物不存在高权限密钥。

Auth 配置使用明确的后台生产 Origin 和实际开发回调路径，例如本地固定开发端口的 `/auth/callback`、`/reset-password`；正式域名使用准确地址，不开放任意跳转。若使用预览域名，仅加入受控项目需要的地址，回调后的 next 参数也限制站内路径。

阶段顺序依赖：生产域名若在本阶段已确认，立即登记；若要到第四阶段创建 Vercel 项目后才取得稳定地址，则本阶段完成开发／测试回调，第四阶段补登记真实部署地址并重新执行登录及重置回调测试。不得将这一待办算作已经完成。

本地管理员／编辑员角色测试可以自动化；云端现有管理员密码登录由本人在正式登录页输入完成，不通过聊天索取密码，不擅自重设密码。泄露密码保护按当前套餐核对可用性及开启情况，单独记录，不把已有 RLS 测试当作该功能已启用。

交付：权限矩阵结果、真实登录证据、Auth URL 配置清单（不含秘密）、安全检查结果。未通过不进入第三阶段。

## 7. 第三阶段：后台集成测试

现有云端只有测试草稿、没有正式公开目录，但未来状态会变化：每次运行前重查公开记录并建立测试白名单。不得复用或覆盖普通产品 ID，不把 HTML 种子／TEST-CLOUD 草稿一键转为正式资料。不凭空补价格、人数或实拍照片；缺少来源的聚仙楼保留草稿并验证发布拒绝。

| 排序与快速新增 | 七类互不影响；整类保存失败旧顺序不变；新增系列／宗教遵守权限及关联规则 |

测试报告逐项记录环境、用例 ID、测试记录 ID、实际结果及证据；区分本地真实 Supabase、云端真实 HTTP 和本人登录验收。完成后只处理白名单内测试资料及文件；曾发布记录遵守隐藏／保留审计规则，不用高权限脚本强删历史来“清理干净”。

交付：端到端报告、数据库回归、Storage 字节访问结果与测试数据清单。未通过不进入第四阶段。

## 8. 第四阶段：双平台部署与测试地址验收

1. 记录原 Vercel 前台项目、当前生产部署、域名与 DNS；核实平台账户授权及 GitHub 集成，保留回退所需配置。
2. 新建 Vercel 后台项目，Root 为 apps/admin，使用独立构建与环境变量；先验收分配地址的深链、刷新、登录及服务端复制／文件补偿。
3. 同仓库新增 Cloudflare Pages 前台项目，Root 为仓库根，构建输出 dist。先部署当前前台到 pages.dev，验证静态资源、SPA 路由、查询参数、详情直达、联系与问卷，保持现有视觉。
4. 配置 SPA 兜底、必要安全响应头及 API 路由；Cloudflare 的配置独立于 vercel.json，不假定复制 Vercel rewrite 即可生效。域名接入先通过 Pages Custom domains 流程，不只手改 CNAME。
5. 回填实际后台域名和必要回调到 Supabase Auth，重新验收第二阶段涉及的真实部署流程。若复制服务只供同源后台使用，优先同源请求；跨源时只开放确需 Origin，并继续验证用户权限。
6. 记录前后台部署 ID、Git SHA、环境变量名称、平台根目录及回滚步骤。旧 Vercel 前台继续保留，测试阶段不改正式 DNS。

本阶段验证“部署架构与测试地址”成功。由于第五阶段才切换数据库源，正式前台域名切换统一放在第五阶段最终验收后，避免刚迁移又因云端 0 发布产品导致空目录。

交付：Vercel 后台地址、Cloudflare 测试地址、部署冒烟报告及回退记录。未通过不进入第五阶段。

## 9. 第五阶段：前台数据库接入与正式上线

1. 保留现有组件视觉与筛选／网格／列表／价格排序行为，抽离 prototypeProducts 直接依赖，新增公开数据 Provider 与 RPC DTO 适配。旧 CatalogProvider、产品页和问卷共享一致的公开产品结果；不保留三份互不更新的售价表。
2. 所有公开产品、宗教、价格、图片及包含项目来自允许公开的 RPC 输出。根据真正公开产品生成筛选选项和数量，停用配置后关联标签、设计图、项目及价格同步移除；不下载 private 全表后在浏览器筛掉草稿。
3. 当前详情地址参数是静态产品 ID，而公开详情 RPC 以 slug 查询。保留现有路径结构，通过已有 slug 或明确的公开旧址映射兼容；不为此擅自新增别名字段或修改既有正式产品 slug。
4. 问卷当前在模块层形成静态产品集合，必须改成接收公开查询结果；保留预算、宗教与人数逻辑、回到结果位置、咨询文字及联系功能。隐藏产品不能继续出现在旧问卷推荐或新咨询摘要中。
5. 实现加载、空列表、网络错误及失效地址。接口故障时不回退到演示种子或旧静态清单冒充已发布资料；区分无产品和读取失败。
6. 发布成功后的新请求读取新数据；已打开页面提供失效刷新／窗口恢复时重取与明确的更新策略。需要 Realtime 时另做订阅权限与断网验收，不把它当作本次强制前提，也不缓存后台私有响应为公开内容。
7. 正式资料录入是独立验收工作：由后台逐件录入／核对真实来源、价格和照片后再发布，不能批量转换 HTML 演示数据。现有云端 0 发布、0 图片是上线阻断条件，必须在切换前解除。
8. 桌面、平板、手机验证；至少覆盖 320、375／390、768、1024、1440 CSS px，检查溢出、触控目标、双栏卡片、1:1 图片、列表、筛选、详情、登录、表单及排序操作。
9. Cloudflare 测试地址完成全链路：后台发布 → 前台出现 → 只改某价格 → 前台更新 → 停用宗教 → 对应内容消失 → 隐藏 → 详情及旧图片请求符合权限。同时执行匿名／普通用户／编辑员的越权测试与构建产物密钥检查。
10. 交付最终验收报告后，确认具体域名与回退方案，再在平台绑定并切换 DNS。核对 HTTPS、跳转、旧链接、缓存、公开目录与问卷；保留旧 Vercel 前台至稳定验收结束，不自动删除。

回滚优先切回已验证部署与 DNS，不自动恢复产品价格或发布状态。数据库接入后的应用故障不能通过静默启用旧静态清单“修复”，以免已隐藏产品重新出现；需要数据恢复时按审计单独评估。

## 10. 每阶段交付与当前待办

每阶段输出一份报告：范围与 Git SHA、执行环境、测试命令及数量、浏览器用例、实际失败与修复、剩余问题、是否满足下一阶段条件。阶段报告明确列出未测项，不把模拟 HTML 的 toast、数据库历史测试或仅页面能打开当作全流程成功。

当前可以开始的下一项是第一阶段的应用骨架、HTML 组件拆分、类型契约与缺失 RPC 开发。正式实施时仍需落实：

- 安放环境待审字段增量的明确决定；否则该功能保持待解决状态。
- 旧前台 Vercel 项目、前后台正式域名及 Cloudflare／DNS 管理权限，第四阶段配置前取得并核实；本计划不猜域名。
- 实际管理员在第二阶段的本人登录，以及测试环境账号与云端测试数据边界。
- 用于最终发布的真实资料及产品图片，不能以测试 PNG 或 HTML 占位图交付。

上述事项按所依赖阶段解决，当前检查与计划无需改动正式数据。暂不进入第一阶段实现，也未将任何阶段标记为完成。

## 11. 部署与认证技术依据
